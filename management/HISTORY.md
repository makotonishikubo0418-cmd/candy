# 履歴管理

更新日: 2026-09-20

## 1. 目的と構成

`HISTORY.md` は、履歴記録を作成・記録・管理するためのルールを定義します。

履歴記録には、今後の開発、改修、調査、障害対応、判断、引き継ぎ、再発防止に必要な事実、決定、対応、結果を保存します。

履歴管理は、以下の4つで構成します。

- `HISTORY.md`: 履歴管理ルール
- `HISTORY_LIST.md`: 履歴案件一覧
- `history/`: 各案件の固定情報を管理する概要ファイル
- `history/records/`: 案件開始後の経過、決定、結果を管理する進捗記録

同一案件について、この構成外に別の履歴台帳を作成してはいけません。

## 2. 基本ルール

- ユーザーから履歴保存を明示的に指示された案件は、必ず記録します。
- ユーザーから明示的な指示がない場合でも、今後の開発、改修、調査、障害対応、判断、引き継ぎ、再発防止に必要な案件は記録します。
- 1つの目的と、その完了条件を1案件として管理します。
- 既存案件と目的および完了条件が同じ場合、新しい案件を作成してはいけません。既存案件に新しい進捗記録を追加します。
- 目的または完了条件を独立して管理する必要がある場合のみ、別案件として作成します。
- 日付、チャット、担当者、AI、メインPC／サブPC、作業フェーズが変わっただけで、別案件を作成してはいけません。
- 確認済み事実、未確認事項、推測を明確に区別します。未確認情報や推測を、確認済み事実として記録してはいけません。
- 通常の会話、重複説明、判断に影響しなかった試行錯誤、個別コマンド、未整理のログや生データは記録しません。
- 現在有効な仕様、ルール、システム構造は、担当する管理書で管理します。履歴記録を現在仕様の正本として使用してはいけません。
- `history/records/` は追記専用です。既存の進捗記録を修正、上書き、削除、移動してはいけません。訂正は必ず新しい進捗記録として記録します。

## 3. 種別とステータス

### 3.1 種別

| 種別 | TYPE | 対象 |
|---|---|---|
| 新規開発 | `CREATE` | 新機能、画面、処理、仕組み、管理書などの新規作成 |
| 改修 | `MODIFY` | 既存機能、仕様、設定、構造、管理書などの変更 |
| 不具合 | `PROBLEM` | バグ、障害、エラー、更新失敗、異常動作などへの対応 |
| 調査 | `INVESTIGATE` | 仕様、原因、構造、状態、影響などの調査、確認、監査 |
| 相談 | `CONSULT` | 方針、仕様、対応方法などの相談、検討 |
| 運用 | `OPERATION` | 本番、サーバー、DB、Git、デプロイ、復旧などの実運用作業 |

種別は、案件全体の主目的に基づいて決定します。

同じ目的が継続している限り、作業フェーズが調査、改修、確認などに変わっただけで種別を変更してはいけません。

### 3.2 ステータス

| ステータス | 使用条件 |
|---|---|
| `Pending` | 案件は登録済みだが、作業未開始 |
| `In Progress` | 現在作業中 |
| `Investigation Pending` | 次に必要な対応が調査または事実確認 |
| `Modification Pending` | 必要な改修が未実施 |
| `Verification Pending` | 作業実施後の確認またはテストが未完了 |
| `Waiting for Response` | 回答、情報、承認、外部対応などを待っている状態 |
| `On Hold` | 意図的に作業を中断している状態 |
| `Completed` | すべての完了条件を満たし、残作業がない状態 |
| `Cancelled` | 対応しないことを決定し、案件を終了した状態 |

ステータスは、実際の現在状態に合わせて設定します。

`Waiting for Response` の場合、何の回答、情報、承認、対応を待っているのかを正確に記録します。

`On Hold` の場合、中断理由と再開条件を記録します。

## 4. 新規案件の登録

新しい案件を作成する前に、既存の案件概要ファイルを確認します。

既存案件と目的および完了条件が同じ場合、新しい案件を作成してはいけません。

新規案件は、以下の順序で登録します。

1. 種別を決定する。
2. 目的、対象範囲、完了条件を定義する。
3. `history/` 配下に案件概要ファイルを作成する。
4. `history/records/` 配下に最初の進捗記録を作成する。
5. `HISTORY_LIST.md` に案件を1行登録する。

緊急時は、安全確保と影響拡大防止を優先し、安全に記録できる最初の時点で履歴を作成します。

## 5. 案件概要ファイル

案件概要ファイルは、案件の固定情報を管理します。

### 5.1 ファイル名

YYYYMMDD_TYPE_subject.md

- `YYYYMMDD`: 案件を最初に登録した日
- `TYPE`: 第3章で定義した種別
- `subject`: 案件を明確に識別できる短い英語のケバブケース

例:

20260901_CREATE_new-function.md
20260901_MODIFY_schedule-update.md
20260901_PROBLEM_girls-manage-500.md
20260901_INVESTIGATE_server-permissions.md
20260901_CONSULT_history-management.md
20260901_OPERATION_production-deployment.md

ステータス変更、完了、キャンセル、作業PC変更を理由にファイル名を変更してはいけません。

### 5.2 必須内容

案件概要ファイルには、以下のみを記載します。

# タイトル

- Type:
- Start Date: YYYY-MM-DD

## 目的

## 対象範囲

## 完了条件

## 初期情報

`初期情報` には、案件作成時点で判明していた、案件を理解するために必要な背景情報のみを記載します。

未確認情報を記載する必要がある場合は、未確認であることを明記します。

現在のステータス、決定、対応、結果、残作業、次の対応、最終結果を案件概要ファイルに記録してはいけません。

作成後は、進捗を反映する目的だけで案件概要ファイルを変更してはいけません。

案件概要ファイル自体に誤りがある場合は訂正できます。訂正によって意味が変わる場合は、その理由と訂正内容も新しい進捗記録に記録します。

## 6. 進捗記録

進捗記録では、案件開始後の確認済み事実、決定、対応、結果、現在状態を管理します。

### 6.1 作成条件

以下のいずれかが発生した場合、新しい進捗記録を作成します。

- その後の判断や対応に影響する新しい事実が確認された。
- 方針、仕様、対応方法、対象範囲が決定または変更された。
- ユーザーから、案件の進め方、条件、決定内容を変更する指示があった。
- 調査、改修、設定変更、確認、本番作業、Git操作などの一単位が完了し、明確な結果が出た。
- 外部からの回答、情報、承認、対応によって、案件のステータスまたは次に必要な対応が変わった。
- `Status`、`Remaining Work`、`Next Action` が実質的に変わった。
- 案件が完了またはキャンセルされた。
- 過去の記録を訂正する必要が生じた。

以下だけを理由に進捗記録を作成してはいけません。

- 単純な質問と回答
- 同じ情報の再確認
- 結論に影響しなかった試行錯誤
- 単独では結果を生まない個別コマンド
- 新しい事実、決定、結果が出ていない途中段階の調査
- 意味を変更しない文章または書式の修正

1つの進捗記録には、1つの作業または判断単位と、その結果を記録します。

### 6.2 ファイル名

YYYYMMDD_TYPE_subject_YYYYMMDD_N.md

先頭の `YYYYMMDD_TYPE_subject` 部分は、対応する案件概要ファイル名と完全に一致させます。

末尾の意味は以下のとおりです。

- `YYYYMMDD`: 進捗記録を作成した日
- `N`: 同一案件・同一日における連番

同一案件・同一日では `1` から開始し、現在の最大連番に `1` を加えた番号を使用します。

日付が変わった場合、連番は `1` から再開します。

欠番があっても、過去に使用した連番を再利用してはいけません。

例:

20260523_PROBLEM_server-compromise_20260912_1.md
20260523_PROBLEM_server-compromise_20260912_2.md
20260523_PROBLEM_-server-compromise_20260913_1.md

### 6.3 標準構成

# タイトル

- History: [`YYYYMMDD_TYPE_subject.md`](../YYYYMMDD_TYPE_subject.md)
- Record Date: YYYY-MM-DD
- Sequence: N
- Status:

## 記録

### 確認済み事実

### 決定

### 対応

### 結果

## 現在

- Remaining Work:
- Next Action:

`確認済み事実`、`決定`、`対応`、`結果` は、その記録に必要な項目のみ使用します。

過去の進捗記録ですでに記録されている内容を繰り返してはいけません。

### 6.4 現在状態の判定

案件の現在状態は、最新の進捗記録から判定します。

最新の進捗記録は、以下の順序で決定します。

1. ファイル名末尾の `YYYYMMDD` が最も新しい記録。
2. 同じ日付の記録が複数ある場合、数値 `N` が最も大きい記録。

その最新記録に記載された `Status`、`Remaining Work`、`Next Action` が、案件の現在状態を定義します。

## 7. 完了、キャンセル、再開、訂正

### 7.1 完了

すべての完了条件を満たし、残作業がない場合のみ、案件を `Completed` にします。

案件を完了する場合、少なくとも以下を含む新しい進捗記録を作成します。

- Status: Completed

### 結果

最終確認済み結果

## 現在

- Remaining Work: None
- Next Action: None

### 7.2 キャンセル

対応しないことを決定した場合、キャンセル理由と以下の最終状態を含む新しい進捗記録を作成します。

- Status: Cancelled

## 現在

- Remaining Work: None
- Next Action: None

### 7.3 再開

未完了案件を再開する場合、同じ案件概要ファイルを継続して使用し、新しい進捗記録を追加します。

`Completed` または `Cancelled` が誤って記録されていた場合、過去の記録を変更してはいけません。誤り、理由、訂正後の現在状態を記載した新しい進捗記録を作成します。

正しく完了した案件の後に、別の新しい問題、依頼、変更が発生した場合は、新規案件として登録します。

### 7.4 訂正

保存済み記録の意味が変わる訂正を行う場合、元ファイルを変更してはいけません。新しい進捗記録を追加します。

訂正記録には、必ず以下を記載します。

- 訂正対象ファイル
- 誤っていた情報
- 正しい情報
- 訂正の根拠

## 8. HISTORY_LIST.md

`HISTORY_LIST.md` は、履歴案件一覧と案件概要ファイルへのリンクのみを管理します。

1案件につき1行登録します。`history/records/` 配下の進捗記録は登録しません。

標準構成:

# Sugar 履歴一覧

更新日: YYYY-MM-DD

| Type | Title | History |
|---|---|---|

ルール:

- 新規案件を作成したときに1行追加します。
- 同じ案件を複数回登録してはいけません。
- 案件概要ファイルが存在しない案件を登録してはいけません。
- `HISTORY_LIST.md` では、ステータス、残作業、次の対応、完了、キャンセルを管理してはいけません。
- 案件の進捗またはステータスが変わっただけで `HISTORY_LIST.md` を更新してはいけません。
- 既存行を変更できるのは、タイトル、種別、案件概要ファイル参照を訂正する場合のみです。
- 案件は開始日の新しい順に並べます。

## 9. メインPC／サブPC運用

メインPCとサブPCの両方から、同じ案件に進捗記録を追加できます。

進捗記録を作成する前に、`GIT_MANAGEMENT.md` に従って、作業PCの `management` ブランチとGitHubの最新状態を比較し、対象案件・対象日における現在の最大連番を確認します。

メインPCとサブPCが同じ連番を同時に作成した場合、GitHubへ先にPushされたファイルを残します。

後からPushする側は、先にPushされたファイルを変更または削除してはいけません。自分側でまだPushしていない記録だけを、次の未使用連番に変更してからPushします。

例:

メインPC:
_20260912_4.md を先にPush。

サブPC:
_20260912_4.md を独立して作成済み。

必要な対応:
メインPCの _4.md を保持する。
サブPC側の未Push記録を _5.md に変更する。

履歴記録の競合解決に強制上書きを使用してはいけません。

すべてのGit操作は `GIT_MANAGEMENT.md` に従います。
